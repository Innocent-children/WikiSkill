# 手动选择与自动演化

当前实现保留“选择会话 → 提取 Wiki → 生成 Skill”的手动入口，并提供可选全自动模式。它替代早期 `raw-webui-platform` 规格中的阈值调度和只生成项目汇总 Skill 的设计。

## 职责

- `session_import.py`：只在请求时枚举本机 Codex 会话、导入选定文件并固定待分析记录。列出会话仅读取文件头部和少量标题内容，不写入 Raw 或调用模型。
- `capture.py`：自动模式的增量原文字节采集，独立于模型；手动模式可显式执行一次导入。
- `runtime.py`：定时调度、固定输入、执行状态、并发检查、消费关系和发布协调。
- `generation.py`：两阶段分析要求与按需多轮读取。只允许读取保存于本批上下文的材料，无任意文件、Shell 或网络工具。
- `evolution.py`：Wiki 原文来源、生成上下文、Skill 来源文件及人工反馈。
- `skill_generation.py`：手动 Wiki 选择、新建和明确合并，已有来源关联优先于关键词排序。
- `skills.py` / `install.py`：生成目录发布恢复、历史恢复，以及独立安装。

## 调度和输入

自动扫描起始时间由 `automatic_scan_since` 配置，使用包含时区的 ISO 日期时间，默认当前时间，初始化或保存设置时写入配置后固定。设置页面按本地时区展示，可选择日期时间或点击“使用当前时间”。自动扫描仍枚举 `sessions` 和 `archived_sessions` 下的 JSONL 路径，但会先检查文件最后修改时间，早于起始时间的文件直接跳过，不打开或逐行读取正文。符合条件的新会话采集完整原文，已有采集位置的会话继续增量读取；因此老会话新增消息后也可能进入采集范围，此设置不是逐条消息时间过滤。修改时间范围不会删除已采集记录或取消已有批次。手动选择会话和显式导入历史不受此时间限制。

`capture_mode` 为 `manual` 或 `automatic`，默认 `manual`。自动模式按 Codex 会话等待连续 1 小时没有新增记录，且可识别轮次全部结束，才创建 Raw 批次；调度仍遵守 `analysis_interval_minutes`。静默时间从最近采集到的新记录计算，同时检查源文件最后修改时间和采集位置，文件新增内容尚未采集时也继续等待。手动导入的旧记录首次进入数据库后同样等待 1 小时。每个批次只包含一个会话未处理且已结束的轮次；中断也可结束轮次，但不会因此被判为成功。同一会话原文保持完整，不按大小继续拆分。缺少会话 ID 时按轨迹来源 identity 分组。

自动 Raw 批次排队和真正开始执行前都会检查会话静默条件。等待期间出现新记录就延后执行，满足条件后将同一会话新增的待处理记录一起加入批次；等待静默的批次不阻塞其他可执行批次。已经开始的模型请求继续完成。手动选择会话、手动执行批次和明确重试沿用立即执行的规则。

手动整理全部、整理选定记录和多会话导入分析使用相同的会话分组方式。创建批次时固定原始记录 ID，执行时读取最新 Wiki，worker 依次处理各批。已有等待、执行中或失败批次的会话暂停新增批次，其他会话继续整理；手动整理全部跳过这些会话，明确选中忙碌会话时提示处理已有批次。

点击“使用当前设置重新生成”时，使用原批次的会话记录重新读取当前 Wiki 并分析。重新生成须用户主动操作。

Wiki 实际修改生成新版本。自动模式按 `skill_wiki` 找到关联 Skill；未关联页面按页面名与项目标识生成独立专题 Skill。一个共享 Skill 同时最多有一批，后续项目变更留待处理。无可复用改动也是有效结果，会记录已检查来源，避免无限重复生成。生成和安装分开。

模式改变时正在执行的模型请求继续完成，下一轮调度重新读取配置。未执行的自动批次在手动模式暂停，执行记录提供手动执行入口；明确重试也可执行该批。失败不自动重新生成。

## 分析协议与用量

原始附录 E.2/E.3 提示词位于 `wikiskill/live/prompts`，项目只在运行时追加明确的接口和业务条件，差异记录于 ADAPTATIONS.md。

Wiki Maintainer 接收选定轨迹、当前完整模式页、目录和日志。返回 `create_patterns / update_patterns / update_index / append_log`。Ollama 请求的 `format` 和本地 jsonschema 校验使用同一份 Schema；已有页面的补丁目标由真实唯一行、段落或章节生成候选，防止模型拼错旧文本。所有模式页、目录和日志在同一事务中更新；并发编辑会整批拒绝。`wiki_documents` 单独保存目录和日志，不触发生成无关专题 Skill。

Skill Proposer 使用真正的 `read_file(path)` 和 `finish(proposal)` 工具。finish 的函数参数直接组成提案对象，包含 `action=create/patch/no_action` 及对应字段，没有额外 proposal 包装。Ollama 原生参数对象、Chat Completions 的 JSON 参数字符串及 Gemini 调用签名分别由适配器处理。Codex 使用 app-server 动态工具（experimental API），宿主仅接受本线程的 read_file/finish 回调。

Proposer 先读取目录和历史，修改前读取所选模式页、可用轨迹（至少四条，不足四条时读全部）、已有 Skill 及最近负面反馈对应的修改。允许读取的文本资源来自目标 Skill 的固定快照。普通文字不能作为最终提案；只有通过结构和业务校验的 finish 才能发布，且不能与读取调用混在同一响应。新建 Skill 必须有 YAML 头部及 PURPOSE.md；补丁保持原有资源和来源历史。无具体任务知识时返回 no_action，禁止将生成器自己的操作说明编造成业务 Skill。

Ollama 使用原生 `/api/chat`，显式 `think=false`、`stream=false`、temperature 0。Maintainer 使用 `format`，Proposer 使用 `tools`，两者分开。API Maintainer 使用 response_format 或 Gemini responseJsonSchema；不支持结构化输出的服务明确失败，不静默改回裸文本。

模型需要材料时继续调用，返回最终结果时结束；手动、自动模式均无 token 或调用次数上限。调用次数和服务返回的 usage 仅作记录，Codex 按 app-server 会话轮次记录，不推算内部模型调用次数。模型服务仍自行处理容量限制。失败批次保留输入，不自动反复重试，不用额外模型调用猜测或修复 JSON。

响应在解析前保存到 `reports/model-responses/<job>/<attempt>-<sequence>.json`，文件权限 0600。保存响应而非认证请求头，不记录 API key 配置。WebUI 的“模型响应原文与工具调用”分页展示所有保留尝试，读取记录不调用模型。连接失败、尚未收到响应时没有响应文件，以批次错误为准。

## 来源与反馈

`wiki_sources(change_id,record_id)` 将 Wiki 正文版本关联到原始记录。后续编辑保留已有来源，新分析追加有效来源。旧生成页面可从其保存的 Raw 批次追溯；人工新建或 ZIP 导入页面没有原文时保持未知。来源表示关联记录，不证明正文每一句话都成立。

`skill_wiki(skill,project,name,change_id)` 记录每个 Skill 已处理的 Wiki 版本。手动选择或自动生成都使用当前正文，历史版本只用来解释修改过程。已有页面全文不变时不会产生无意义版本。

`skill_feedback` 记录选定已发布版本的实际结果、问题、拒绝原因与备注。恢复历史内容时额外记录替换前版本与恢复目标。反馈保留完整文本，在后续批次固定下来；批次期间新增反馈留给下一次生成。反馈不会触发模型或自动回退。

实际修改发布时，由宿主将选中 Wiki 版本和修改摘要追加到 `PURPOSE.md`，与 `SKILL.md` 在同一次完整目录快照中发布、恢复和安装。Wiki 的已有版本记录和批次摘要组成知识演化日志，生成器可以按需查阅。

## 验证范围

核心检查覆盖手动会话选择、零模型导入、定时双阶段处理、按主题关联、模式热切换、暂停批次、失败停止、材料范围检查、原文来源、负面反馈、历史正文纠正、PURPOSE 发布及目录恢复；API 协议使用本地服务桩，Codex 使用 app-server 协议桩。

这些检查确认程序行为。真实模型提炼效果需要实际模型和业务会话验证，不以固定响应测试代替效果评测。

真实 Ollama 检查使用 qwen3.5:9b（Q4_K_M）和合成轨迹，覆盖创建、补丁和 no_action。可通过 scripts/verify_ollama_workflow.py 显式复验自动生成与手动 no_action；模型响应保留于隔离数据目录。服务启动测试在前端构建完成后执行，避免构建清空资源目录干扰检查。
